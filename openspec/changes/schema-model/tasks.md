## 2. Schema name selection
<!-- kind: behavior -->

This group is entirely pure: `schema_key`, `is_legal_name`, and `declared_name` take `&str`
and `FileText` values and touch no filesystem. Group 3 adds the edge that produces those
values. Splitting them this way is what lets these eleven scenarios run without a scratch
tree, and it is the same move `resolve::path_candidates` made for the `PATH` string.

- [x] 2.1 RED: Write failing unit tests in `src/schema.rs`, one per spec scenario, named after them: "A change's own declaration wins over the project's", "The project declaration answers when the change declares nothing", "Nothing declared anywhere yields the default", "A blank declaration is not a declaration", "A declaration of the wrong type is not a declaration", "A file that is not valid YAML falls through and is named", "An empty or comment-only document declares nothing without complaint", "A file that declares other keys but no `schema:` records no problem", "A fallback at both sources records both problems, in order", "Only the first YAML document is consulted", "A name containing a path separator is rejected and falls through", "Every rejected shape is rejected, and a legal name with a dot is not", "An illegal project name still falls through to the default". Build every input as a `&str` literal and a `FileText` value; no test in this group creates a file
- [x] 2.2 RED: Make the precedence test discriminating rather than merely green-able. "A change's own declaration wins over the project's" must **also** assert, in the same test, that dropping the change source yields the project's name — otherwise an implementation that ignores the project file entirely passes, and so does one that ignores the change file when the two happen to agree. Assert the whole `Selection` value with `assert_eq!`, including `source` and `problems`, not just the name
- [x] 2.3 RED: "Nothing declared anywhere yields the default" must assert `problems.is_empty()`, not only the name. This is the absent-dependency case for both configuration files at once, and the empty-problems clause is the only thing that rejects an implementation recording a fallback for a file that never existed — which would put a spurious message in the header for every repository that simply uses the default
- [x] 2.3a RED: "A file that declares other keys but no `schema:` records no problem" is the case an implementation gets wrong by accident, and it is the reason `schema_key`'s wrong-type branch must be keyed on `!is_badvalue()` rather than on `as_str().is_none()`. `yaml-rust2` yields `Yaml::BadValue` for a missing key, whose `as_str()` is `None` — **identical** through a string accessor to `schema: [a]`, which must record a problem. Assert `Ok(None)` from `schema_key` for a mapping carrying `context:` and `rules:` and no `schema:`, and for a `.openspec.yaml` carrying only `created:`, then `problems.is_empty()` through `declared_name`. This is the ordinary shape of a repository that pins nothing, and it is the single most common real input in the change
- [x] 2.3b RED: "A fallback at both sources records both problems, in order" is the only scenario in which both sources fail at once — a blank `.openspec.yaml` value and a mapping-valued `schema:` in `openspec/config.yaml`. Assert `problems.len() == 2` with the change file's message first. Every other scenario in this group asserts *exactly one* problem from a single file, so without this one an implementation that returns on the first problem, keeps only the last, or stores an `Option<String>` rather than the `Vec` the requirement invokes passes the whole group
- [x] 2.4 RED: "A declaration of the wrong type is not a declaration" asserts four values in one test — a nested mapping, a sequence, `null`, and a document that is a bare top-level scalar rather than a mapping. An implementation that string-formats any YAML node returns `{...}` or `[...]` as a schema name and fails all four; one that only handles the mapping case fails the rest. "A blank declaration is not a declaration" asserts both `"   "` and `""` in one test, reusing the `config::non_blank` rule rather than restating it
- [x] 2.5 RED: "An empty or comment-only document declares nothing without complaint" asserts `problems.is_empty()` for both inputs. `yaml-rust2` returns **zero documents** for each (verified), so an implementation indexing `[0]` panics here rather than failing an assertion — check the test reports a panic and not a compile error, so the RED is the behaviour and not the harness
- [x] 2.6 RED: "Every rejected shape is rejected, and a legal name with a dot is not" asserts seven values in one test — `..`, `.`, `a/b`, `a\b`, `/abs`, a value containing a NUL byte, and `v1.2-tdd`. Write the NUL fixture as the YAML **double-quoted escape** — document text `schema: "a\0b"`, i.e. the Rust literal `"schema: \"a\\0b\"\n"` — because a literal NUL in a plain scalar is silently truncated to the perfectly legal name `a` (verified), after which the test goes red for a reason unrelated to `is_legal_name` and the likeliest repair is to weaken the assertion. "A file that is not valid YAML falls through and is named" asserts that the problem text contains the parser's own message, not a generic one, so a user can find the offending line
- [x] 2.7 Confirm every failure is the missing function rather than a broken test module — check that `cargo test --all-features schema::` **names** the new tests rather than reporting "0 passed … N filtered out", which a cargo test-name filter does for any nonsense filter and returns 0
- [x] 2.8 GREEN: Implement `schema_key(text: &str) -> Result<Option<String>, String>`. `Ok(None)` when the text holds no document; `Err` when it is not valid YAML, when its first document is not a mapping, or when `schema:` is present with a value that is not a string — including `null`. `Ok(Some(trimmed))` for a non-blank string, applying `config::non_blank`'s rule. Then `declared_name(change, project) -> Selection` walking the three sources in order, treating an `Err` from `schema_key` and an illegal name identically: record one problem naming the file and continue to the next source, never win and never stop. `FileText::Absent` contributes nothing and records nothing; `FileText::Unreadable` records one problem naming the file
